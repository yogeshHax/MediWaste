# VerifyPoint station protocol — v1

One protocol, four implementations: phone BLE client (`/station/ble`), ESP32
firmware (`firmware/esp32/`), trusted backend (`functions/`), simulator
(`/simulator`). Types live in `src/lib/station/protocol.ts` (Zod).

## Frames (newline-delimited JSON over BLE; HTTPS body for backend)

**Request — phone → ESP32 → backend**

```json
{"v":1,"msgId":"m-a1b2c3","stationId":"station-1","operation":"inspection_started","donationId":"MW-AB12CD34","actorUid":"uid…","sentAt":1730000000000}
```

**Transport ack — ESP32 → phone** (means "received", NOT "approved")

```json
{"v":1,"type":"ack","echo":"m-a1b2c3"}
```

**Error — ESP32 → phone** (transport-level rejection)

```json
{"v":1,"type":"error","reason":"malformed|unsupported_version|busy|duplicate","echo":"m-a1b2c3"}
```

**Response — backend → ESP32 → phone**

```json
{"v":1,"msgId":"m-a1b2c3","ack":true,"status":"REQUEST_ACCEPTED","currentStatus":"inspection_in_progress","donationCode":"MW-AB12CD34","detail":"Accepted","appliedAt":1730000000123}
```

## Operations

| Operation | Permitted from | Moves record to |
|---|---|---|
| `intake_registered` | awaiting_inspection | awaiting_inspection (check-in) |
| `inspection_started` | awaiting_inspection, inspection_in_progress | inspection_in_progress |
| `inspection_completed` | inspection_in_progress | pending_verification |
| `review_decision` | pending_verification, quarantined_for_review, awaiting_authorised_decision | awaiting_authorised_decision (dashboard records the actual decision) |

## Status codes

| Status | Meaning | Gate opens |
|---|---|---|
| `REQUEST_FOUND` | record exists, no transition due | no |
| `REQUEST_ACCEPTED` | authorised transition applied | **yes (only this)** |
| `UNKNOWN_ID` | no record with that ID | no |
| `ALREADY_PROCESSED` | msgId already applied | no |
| `REQUIRES_REVIEW` | quarantined pending review | no |
| `NOT_ELIGIBLE_FOR_NEXT_STAGE` | current state forbids transition | no |
| `UNAUTHORISED` | identity/token/reviewer check failed | no |
| `INVALID_MESSAGE` | malformed frame | no |
| `NETWORK_ERROR` | transport failure | no |
| `SERVER_ERROR` | backend failure | no |

## Rules

1. `msgId` is generated by the phone (unique per message); the backend records
   it in a per-donation ledger — duplicates return `ALREADY_PROCESSED`.
2. The backend re-reads the donation's CURRENT stored state; nothing client
   supplied about the record is trusted.
3. An existing record never proves medicine quality or reuse-eligibility; only
   the authorised inspection + review workflow does.
4. ESP32 authentication = per-station bearer token (never a Firebase admin key).
5. All state changes are applied in a Firestore transaction together with an
   audit event and the msgId ledger entry.
